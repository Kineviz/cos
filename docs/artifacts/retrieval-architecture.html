How Kiran finds answers

What happens between your question and the reply, what was broken, and what we fixed. Every number here was measured, not estimated.

The problem: search ignored dates

You asked how your talk went this morning. The search found emails from February 2026 and November 2025 — the wrong months. The answer came out right anyway, through luck: there were so few emails on that topic that the best match happened to be the right one. On a common topic, that luck runs out.

Why did this happen? Every page in the brain has a date. Search never looked at it. There was also no way to ask "what happened between these two dates" at all. The search tools take no date input.

The fix was not better search-by-meaning. The fix was adding a second way to find pages: by date.

The path a question takes

Two notes on this picture. First, the model can also search on its own if the six pages are not enough. That is why a bad first search often still produced a right answer — just slowly. Second, we hand the model the six pages directly, so it does not waste time finding them again.

Kiran now searches four ways at once

Each way is good at something the others cannot do. Until today, only the first one was used.

Vector search is the right default, but it should not be the only one. The rule now: a question with a topic is found by meaning and ordered by time; a question with only a time is found by time. To tell which kind a question is, we remove the time phrase and see whether anything is left.

The five bugs we measured

1. Ranking ignored dates

Every page has a date. Ranking never looked at it. A page from 2015 and a page from yesterday competed as equals. Here is a real query — every result is from the wrong year:

query: "audience reaction to my presentation" 0.893 2025-10-07 great-presentation 0.545 2023-11-16 my-presentation-to-niaid-today 0.538 2022-03-20 presentation 0.532 2022-10-28 presentation-went-very-well nothing from 2026.

2. "What happened between these dates" could not be asked

No search tool takes a date. The one index that was built for dates was never filled — it has 120 entries for 62,781 pages, so it returns nothing for any real day.

timeline_entry_count 120 page_count 62,781 chronicle_day("2026-08-07") → []

3. A third of search results had a blank date field

A date-aware ranker is useless on a page with no date. But the date was never really missing — 99.9% of files have it in the file name. We now read it from there.

11 of 30 rows had effective_date = null 27,448 of 27,477 files carry the date in the filename

4. The graph had links that led nowhere

The brain has 13,000 links between emails and people. Search never used them. When we tried to use them, we found most were broken: emails link to people pages, but the importer never created those pages. Of 863 people the emails link to, only 8 had a page.

We created the 658 missing pages from data the importer already had. Now the links work. From one person, Kiran can reach their meetings and the people in those meetings.

person pages 8 → 666 resolved links 2 → 36,978 meeting edges 0 → 5,264 two-hop reach 1 → 39 nodes

5. Junk mail competes with real mail

Nothing marks a system alert or a newsletter as junk, so they compete with real conversations for the six document slots. The single biggest page in the brain is a repeated system alert. Not fixed yet.

From 70 candidates down to 6

You asked: is the filter step important? Yes, and we have proof. When we once gave the model everything we had, accuracy dropped 18 points in one run. More context made answers worse. Choosing well matters more than sending more.

Here is how we choose. The four searches return about 70 candidate pages. We keep 6. The rules:

Pages found by several methods rank first. If the meaning search, the keyword search, and the graph all found the same page, that page is probably the right one.

But each method's #1 pick is guaranteed a spot. Without this rule, a page that one method was sure about could get buried. It happened: the page about the DataCon talk was #1 in one search and #30 in another, so on average it ranked #8 and got cut.

No repeats. One email thread gets at most one spot. One person gets at most two. Otherwise all six spots go to one long conversation.

Newer beats older — a little. If two pages match equally well, the newer one wins. The nudge is kept small on purpose: the email that names Northwind's decision maker is from 2025, and a strong "prefer new" rule would hide it. Only when you say "lately" does the date become the main factor.

Your question about meeting transcripts

You worried that meeting notes with a summary plus a raw transcript would flood the context with useless text. I checked: there are no transcripts in the brain yet. The 1,613 calendar pages are just invitations. So we can set the rule now, before the first transcript arrives.

The rule I recommend: search the summary, never the transcript. Keep the transcript on the page so you can open and read it. But do not put it in the search index. A transcript mentions the topic fifty times in small talk; a summary states it once. If both are searchable, the transcript wins the search and pushes out the summary — the exact opposite of what you want.

The same problem already exists with email. Threads are stored whole, with every quoted reply and signature. That is why the biggest page in the brain is a repeated system alert.

What is fixed, and what is not

Fixed: dates now work. "This morning", "last week", and "in July" turn into real date ranges. We include a day on each side, because you once asked about "this morning" when the talk was the morning before. And the 37% of search results that had a blank date field are handled too — the date was in the file name all along, so we read it from there.

Fixed, partly: the graph is connected. A name in your question now leads to a person, and a company name leads to the people who write from that company's email domain. From there we pull the emails and meetings that mention them. We only follow one step of connections so far. Going deeper might give better answers; we have not tested that yet.

Not fixed: junk competes with real email. Nothing marks a newsletter or a system alert as junk, so they compete for the same six spots as real conversations. The single biggest page in the brain is a repeated system alert.

Decision needed soon: transcripts. See the section above. The rule should be in place before the first transcript arrives.
