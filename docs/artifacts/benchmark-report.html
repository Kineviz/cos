First: the scores are noisy

We ran the same test twice with nothing changed. Run 6 scored 94%. Run 7 scored 100%. Same code, same questions, same data.

So a 6-point difference means nothing. One question flipping is worth 6 points, because there are only 17 questions. When two runs are within 6 points of each other, we cannot say which one is better.

Speed is even noisier. In those two identical runs, one question took 213 seconds the first time and 28 seconds the second time.

Run 6 → run 7
±6 pts · 1 of 17

Why do questions flip? So far, always the same reason: a timeout. The model sometimes keeps searching until the 5-minute limit kills it. The same question finishes fine on the next run.

But this score has a blind spot. It only checks which documents Kiran found. It does not check what Kiran did with them. Later in this page, recall breaks for six runs while this score stays at a healthy 93% — because Kiran was finding the right documents and still giving wrong answers. Keep that in mind when reading it.

How the test works

17 questions, 5 categories: dates and times, remembering facts, lists, reasoning, and honesty (questions about things that do not exist, where the right answer is "I don't know"). Each answer is checked for specific facts. For example: the answer to "who is the decision maker at Northwind" must contain "Morgan". No AI grades the answers. A string is there or it is not.

Two code reviews also ran on day one. They found one security hole, one bug that could lose data, and about thirty smaller problems. The two worst are below.

What the reviews found, worst first

Any web page could rewrite your settings

The settings endpoint accepted changes from anywhere. No check on where the request came from. So any web page open in your browser could quietly change Kiran's settings: who it may email, where it may write files, and the API key.

We proved it before fixing it: from a browser tab, we renamed the agent to PWNED. It worked. The IP allowlist did not block it, because the request really did come from this machine.

It is fixed and re-tested. The attack now fails. Normal requests still work.

A torn write could silently erase every manual to-do

If two saves happened at the same time, the to-do file could get scrambled. The page would then show an empty list, as if you had no to-dos. Your manual items exist only in that file. There was no backup.

It is fixed: saves now wait for each other, a backup is kept, and a scrambled file shows an error instead of an empty list. A test runs 12 saves at once and checks that all 12 survive.

Three signals that pointed the wrong way

Three parts of the system could report good news that was false. A command could fail but still get saved as a good answer. A health check could text you "🟢 Recovered" when the real status was unknown — this happened during a real outage. And a question that timed out just disappeared from the page, instead of showing as failed.

All three are fixed. The common mistake: treating "no bad news" as good news.

Your two reported bugs

"It never finished." The dashboard was loading 47 plugins and over 200 tools into the model. With that much to choose from, it looped until the 5-minute limit killed it. We cut the tool list down to the two it needs. The same question now answers in 21 seconds. Telegram never had this problem — its tool list was already short.

"Many irrelevant docs." Kiran picks which database to search based on the folder it starts in. It was starting in the wrong folder. Searching "falcon" from the wrong folder returned four unrelated people. From the right folder: six Falcon email threads. We pinned the folder.

"It ignored 'this morning'." We now put today's date in the prompt instead of hoping the model checks the clock.

Two questions broke and stayed broken for six runs

From run 12 to run 16, two of the six memory questions kept failing. Six runs in a row is not luck. Something was broken.

My first guess was wrong. I blamed the 666 people pages we created for the graph that afternoon. But the timeline disproves it: the questions broke at run 12, hours before those pages existed.

The real clue: both broken questions still got a perfect score on finding documents. Kiran found the right documents and still gave wrong answers. So the problem was in what happened after the documents were found. There were two separate bugs.

"What did we discuss on Falcon lately?"
newest thread 68 days old
…but "lately" meant a 30-day window
0 pages qualified

Bug 1: "lately" was defined as "the last 30 days". The newest Falcon email is 68 days old. So the 30-day rule matched nothing, and the date stopped mattering. Old emails from 2024 won because their wording matched the question better. The fix: "lately" now means "the newest pages about this topic", with no day limit.

Bug 2: we only sent the model the top of each document. The answer to "why has the Northwind deal stalled?" is one line in your task dashboard: "stalled because their security review is stuck". But that line is deep in the page, and we only sent the model the first 1,200 characters. Kiran had the right document and could not see the answer inside it. The fix: we now send the part of the document that mentions the question, not always the top.

After both fixes, all six memory questions pass again. They have passed in every run since.

The same digging found two more bugs

"Last week" was answered with one day. That Friday had 8 meetings. They filled all six document slots, so no other day made it in. The answer described Friday and called it the week. Fix: each day of the week now gets a turn before any day gets a second one.

A document that only one search method liked got buried. We combine results from several search methods by averaging their rankings. The page about the DataCon talk was ranked #1 by one method and #30 by another, so it averaged out to #8 — and only the top 6 get used. Fix: each search method's #1 pick is now guaranteed a spot.

The bottom six questions can be answered from data we already have on hand: the date, the to-do list, the list of people waiting. They take 13–23 seconds. The top eleven need to read documents. They take 4 to 15 times longer.

Every question pays a 13-second startup fee

"What is today's date?" needs no search and no reading. It still took 13 seconds. Why: every question used to start a fresh copy of the assistant, which loads 47 plugins and registers 109 tools before doing anything. For simple questions, that startup was most of the wait. Simple questions now skip the assistant entirely and answer in about 1 second.

The very slow answers were stuck, not slow

Ten answers in the test's history took exactly 300 seconds. That is the time limit — they were still searching when it cut them off. These were questions where the model had nothing to find, so it never stopped looking. Both "I don't know" questions are in this group. We capped how far a search can widen, and no answer has hit the limit since run 12.

The 17 questions

Each answer must contain certain facts to pass. The facts come from your real data. For example, the decision-maker answer must contain "Morgan". No AI judges the answers — a fact is present or it is not.

Some questions also have a known wrong answer. For the decision-maker question, that is "Taylor". If the answer says Taylor is the decision maker, it fails, no matter how good the rest is.

The last two are the most important in the set. They ask about things that are not in the data at all, and the only right answer is to say so. A confident invented number there is the single most damaging thing this system could do, which is why it is measured on every run. It has never once failed them by inventing — the one loss came from a question that never finished.

Four lessons from 21 runs

1. More context made answers worse. Run 2 added the same block of facts to every question. Accuracy dropped 18 points. The extra text crowded out the documents that the harder questions needed. Give the model less, not more.

2. Different questions need different search. "What did I do last week?" needs a date lookup. "Who is Pat?" needs a name search. One search method cannot serve both. Kiran now runs four search methods and combines them.

3. The slowest answers were infinite loops, not hard questions. Ten answers hit the 5-minute limit. Each one was a search that kept widening because there was nothing to find. We capped the widening. None since run 12.

4. Kiran does not make things up. 374 answers, zero invented facts. It said "I don't know" every time it should have. This was true from the start and stayed true through every change.

What is not done yet

We need fresh questions. We have tuned the system against these 17 questions for two days. It may now be good at these 17 questions rather than good in general. The next real test is a set of questions it has never seen.

Every hard question still pays a 13-second startup fee. Each one starts a fresh assistant, which loads 47 plugins and 109 tools before it starts working. That fee was small when answers took 76 seconds. Now answers take 12 seconds, so the fee is a quarter of the total. The fix is to keep one assistant running and reuse it. Not done yet.

The graph is built but barely used. From one person, Kiran can now reach their meetings and the other people in those meetings — 39 connections where this morning there was 1. But search only uses the first step. We have not yet tested whether going deeper gives better answers.
